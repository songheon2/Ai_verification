# Numerical failure의 원리와 현재 구현

> 상태 변경: 아래 내용은 정확 유리수 검증·원본 식 검사·50자리 복구가 적용되어 있던 당시의 기록이다. 성능 부담으로 해당 추가 기능과 DPLL(T)의 엄격 부등식 재검사를 제거했다. 현재는 추가 전의 부동소수점 탐색과 기본 tableau 일관성·NaN/Inf 검사, 기존 시간·반복·정체 한도 처리를 사용한다. 아래의 복구·정확 검증·검증 예산 설명은 더 이상 현재 동작이 아니다. `NumericalValidation.py`도 제거되었다.

이 문서는 현재 `Simplex.py`, `Reluplex.py`, `NumericalValidation.py`, `DPLL_T.py`의 구현을 설명한다. 외부 검증 도구의 일반적인 동작 설명이 아니라 이 저장소의 실제 처리 기준이다.

## 1. 핵심 의미

`numerical failure`는 **문제가 UNSAT이라는 뜻이 아니라, 계산 상태의 수치적 신뢰성을 확보하지 못해 판정을 보류한다는 뜻**이다.

현재 구현은 빠른 부동소수점 탐색과 최종 결과의 정확 검증을 분리한다. 탐색 도중 수치 불일치가 발견되면 복구를 시도하고, 복구할 수 없거나 판정의 근거를 확인하지 못하면 정상적인 상세 검증 경로에서는 `UNKNOWN`을 반환한다.

다음 두 가지는 구분해야 한다.

- `NUMERICAL_FAILURE`: 계산 상태의 불일치, 비정상 수치 등으로 탐색 결과를 신뢰하기 어렵다.
- `VALIDATION_INCONCLUSIVE`: 정확 검증에서 해 또는 모순을 확인하지 못했다. 검증 예산 부족도 포함하므로, 이것만으로 실제 오차가 발생했다고 단정할 수 없다.

따라서 이 기능은 단순한 그래프 항목이 아니다. SAT/UNSAT 후보의 확정을 막거나, 복구를 통해 다른 후보를 찾게 할 수 있다.

## 2. 부동소수점 오차가 생기는 이유

Simplex는 tableau의 식을 반복해서 변형한다. 예를 들어 다음 식에서 기저변수를 교환하면 계수의 나눗셈·곱셈·덧셈이 발생한다.

```text
x_basic = a * x_entering + b * y
→ x_entering = x_basic / a - (b / a) * y
```

컴퓨터의 `float`는 모든 실수를 정확히 표현하지 못한다. 특히 작은 계수로 나누거나, 큰 값끼리 빼서 작은 결과를 만들 때 오차가 커질 수 있다. 피벗이 반복되면 변형된 계수와 변수 값이 원래 식에서 조금씩 벗어날 수도 있다.

주의할 점은 **현재 tableau와 현재 변수 값이 함께 틀어질 수 있다는 것**이다. 둘끼리만 비교하면 서로 맞아 보이지만 원래 입력 식과는 다를 수 있다. 그래서 피벗 이전의 원본 식을 별도로 보관해 비교한다.

## 3. 일반적인 제약 위반과 수치 실패는 다르다

탐색 중 변수의 경계 위반은 정상적으로 발생할 수 있다. Simplex는 바로 그 위반을 해소하기 위해 피벗한다.

| 상태 | 의미 | 기본 대응 |
| --- | --- | --- |
| `z`, `h`, slack 등이 상한·하한을 벗어남 | 현재 후보가 선형 경계를 만족하지 않음 | 기저·비기저 상태와 이동 가능성에 따라 피벗 탐색 |
| `h != max(0, z)` | 현재 후보가 ReLU 관계를 만족하지 않음 | Reluplex의 repair 또는 분기 |
| 현재 값이 tableau 또는 원본 식과 불일치 | 계산 표현 자체의 신뢰성 문제 | 수치 복구 시도 |
| 피벗이 오래 반복됨 | 탐색 정체 또는 어려운 문제일 수 있음 | 피벗 규칙 전환, 정체·반복·시간 한도 처리 |

즉, **slack 위반이 보였다는 이유만으로 numerical failure가 되는 것은 아니다.** `z`와 `h`도 마찬가지다.

## 4. 현재 오차 허용 기준

### 4.1 식의 일관성 검사

기본 허용 계수는 `DEFAULT_TOL = 1e-9`이다. 현재 tableau와 원본 식 검사에서 다음 조건을 사용한다.

```text
actual   = 저장된 기저변수 값
expected = 식의 우변으로 다시 계산한 값

|actual - expected| <= 1e-9 * max(1, |actual|, |expected|)
```

예를 들면 값의 크기가 1 이하인 식에서는 약 `1e-9`, 값의 크기가 1,000인 식에서는 약 `1e-6`까지 잔차를 허용한다. 경계 근처에서는 실제 scale 값에 따라 기준이 정해진다.

이 값은 **탐색 상태의 일관성을 점검하기 위한 허용오차**다. 신경망 출력 전체의 오차 상한이나 최종 증명의 허용오차를 뜻하지 않는다.

### 4.2 경계 위반 탐색

일반 탐색에서는 경계 값의 크기에 비례하는 허용오차를 사용한다.

```text
lower_tolerance = 1e-9 * max(1, |lower|)
upper_tolerance = 1e-9 * max(1, |upper|)
```

수치 복구 이후에는 피벗 대상을 찾을 때 이 경계 허용오차를 `0`으로 바꾼다. 이전 허용오차에 가려져 있던 작은 실제 경계 위반도 수정할 수 있게 하기 위해서다. 식의 일관성 검사까지 모두 무오차 검사로 바뀌는 것은 아니다.

### 4.3 비정상 수치

변수 값이나 재계산 결과의 `NaN`, `Inf`는 정상적인 유한 해로 인정하지 않는다. 다만 **경계의 `-Inf` 하한·`+Inf` 상한은 무제한 구간 표현으로 허용**한다. `NaN` 경계, `+Inf` 하한, `-Inf` 상한 등은 비정상 경계로 처리한다.

### 4.4 정확 검증

최종 정확 검증에서는 위 `1e-9` 잔차 허용 기준으로 통과시키지 않는다. 유리수 연산으로 등식·부등식·ReLU 관계를 확인한다.

## 5. 언제 검사하는가

Simplex의 주요 검사 지점은 다음과 같다.

1. 시작 시 경계가 비정상 수치인지 확인한다. 하한이 상한보다 큰 직접적인 모순은 UNSAT으로 처리한다.
2. 변수 값 갱신이나 피벗 연산에서 수치 문제가 발생하면 복구를 시도한다.
3. 피벗 **256회마다** 기저변수 값을 재계산하고, 현재 tableau와 원본 식의 일관성을 확인한다. 탐색 중이므로 이때는 경계 만족을 요구하지 않는다.
4. 더 이상 경계를 위반한 기저변수가 없어 SAT 후보가 되면 경계와 식의 일관성을 확인한다.
5. 피벗할 변수를 찾지 못해 UNSAT 후보가 되면 식의 일관성과 정확한 모순을 확인한다.

따라서 검사는 최종 결과에서만 이루어지는 것도, 매 피벗마다 전체 정확 검증을 수행하는 것도 아니다.

## 6. 복구는 어떻게 진행되는가

복구는 **Simplex 호출당 최대 한 번** 수행한다. 전체 신경망 검증에는 Simplex 호출이 여러 번 있을 수 있으므로, 전체 실행에서 한 번이라는 뜻은 아니다.

복구 순서는 다음과 같다.

1. 변형된 tableau 대신 보관한 원본 식으로 tableau를 다시 만든다.
2. 현재 분기의 경계 조건은 유지한다.
3. 원본 기저에서 비기저변수가 되는 변수는 기존의 유한 값을 가능한 범위 안으로 잘라 재사용한다.
4. 기저변수 값은 기존 값을 복사하지 않고 원본 식으로 재계산한다.
5. 재계산에는 십진수 **50자리 중간 연산**을 사용한다.
6. 정체·기저 재방문 기록을 초기화하고, 남아 있는 반복·시간 예산으로 탐색을 재개한다.

복구 이후의 일부 피벗 나눗셈 및 값 갱신에도 50자리 중간 연산을 사용한다. 다만 저장 결과는 다시 `float`로 변환하므로, **복구 경로 전체가 임의정밀도 또는 정확 연산인 것은 아니다.**

복구는 `max_iter`나 전체 deadline을 새로 부여하지 않는다. 다시 문제가 생기거나 복구 자체가 실패하면 해당 이유로 판정을 보류한다. 비정상 입력 경계처럼 바로 실패하는 경로도 있으므로 모든 실패에 재시도가 보장되는 것은 아니다.

## 7. SAT 후보는 어떻게 검증하는가

독립적으로 Simplex를 사용할 때는 기본값 `verify_sat=True`로 선형 해를 정확 검증한다.

Reluplex 내부에서는 비용을 줄이기 위해 중간 Simplex 호출에 `verify_sat=False`를 전달한다. 대신 **최종 비선형 SAT 후보에서 원본 식·경계·ReLU를 함께 정확 검증**한다. 중간 Simplex의 일관성 검사와 UNSAT 검증까지 끄는 것은 아니다.

`NumericalValidation.exact_witness()`는 대략 다음 순서로 동작한다.

1. `float` 후보와 계수를 정확한 유리수로 변환한다.
2. 후보가 원본 등식, 모든 경계, 전달된 ReLU 관계를 정확히 만족하는지 검사한다.
3. 그대로 맞지 않으면 원본 식을 이용해 값을 재계산하거나 정확한 소거 연산으로 해를 재구성한다.
4. 재구성한 해도 모든 조건을 다시 확인한다.
5. 확인된 해를 얻지 못하면 `None`을 반환한다.

ReLU 검증에는 `h = max(0, z)` 관계가 포함된다. 재구성 시 선택한 ReLU 상태에서 해를 못 찾았다고 해서 다른 상태에도 해가 없다는 뜻은 아니다.

Simplex의 정확 검증 실패는 남은 복구 기회가 있으면 재탐색한다. Reluplex 최종 검증에서 해를 확인하지 못하면 `RELUPLEX_VALIDATION_INCONCLUSIVE`로 보류한다.

## 8. UNSAT 후보는 어떻게 검증하는가

부동소수점 tableau에서 피벗할 변수가 없다는 관찰만으로 UNSAT을 확정하지 않는다. 계수 오차 때문에 실제 가능한 이동 방향을 놓쳤을 수도 있기 때문이다.

`NumericalValidation.certify_unsat()`는 원본 식의 정확한 선형 결합으로 모순을 확인한다.

```text
원본 등식에서 유도한 식: L(x) = 0
현재 경계로 계산한 L(x)의 가능한 범위: [2, 5]
→ 0이 포함되지 않으므로 이 경계 아래에서는 모순
```

먼저 현재 충돌 행이 제안하는 선형 결합을 검사하고, 그것으로 부족하면 현재 기저에 해당하는 식을 정확 연산으로 재구성해 검사한다.

반환값 `False`는 **모순을 확인하지 못했다**는 뜻이지 SAT이라는 뜻이 아니다. 일관성이 깨진 경우와 정확 검증만 불확정인 경우는 서로 다른 실패 이유로 구분한다.

한 Simplex 호출의 UNSAT은 해당 분기의 선형 문제에 대한 결과다. 그것이 곧바로 전체 신경망 문제의 UNSAT은 아니다. Reluplex 분기와 DPLL(T)의 나머지 탐색 결과까지 종합해야 한다.

## 9. 전체 판정으로 전달되는 과정

```text
부동소수점 탐색
 ├─ 수치 불일치 → 복구 가능하면 재탐색 → 실패하면 UNKNOWN
 ├─ SAT 후보 → 해당 단계의 검증 통과 → 상위 탐색으로 전달
 │                                      → 최종 ReLU 포함 검증 → SAT
 └─ UNSAT 후보 → 정확 모순 확인 → 해당 분기 UNSAT
                                 → 상위 탐색에서 종합

정확 검증 불확정 → 가능한 복구 또는 UNKNOWN
전체 시간 초과  → TIMEOUT 사유의 UNKNOWN
```

기본 상세 검증 경로에서는 `SolverLimitReached(reason)` 예외로 불확정 상태를 상위에 전달하고, DPLL(T)가 최종 `status=UNKNOWN`과 구체적인 `reason`을 기록한다.

ReLU 분기에서 한쪽이 불확정이고 다른 쪽이 UNSAT이라고 해서 전체를 UNSAT으로 확정하지 않는다. 반대로 다른 쪽에서 검증된 SAT 해를 찾으면 그 해로 SAT을 확정할 수 있다.

주의: 구형 호환 API에서 `report_unknown=False`를 사용하면 일부 실패도 `(None, False)`로 축약된다. 이 반환값만으로 UNSAT과 불확정을 구분해서는 안 된다. 최종 상태 확인에는 상세 결과 API를 사용해야 한다.

## 10. 실패 이유를 구분해서 읽기

| reason 또는 호출 로그 결과 | 의미 |
| --- | --- |
| `SIMPLEX_NUMERICAL_FAILURE` / `NUMERICAL_FAILURE` | 계산 상태의 수치적 신뢰성을 확보하지 못함 |
| `SIMPLEX_VALIDATION_INCONCLUSIVE` / `VALIDATION_INCONCLUSIVE` | 선형 후보의 정확 검증이 불확정이며 복구로도 해결하지 못함 |
| `RELUPLEX_VALIDATION_INCONCLUSIVE` | 최종 ReLU 포함 SAT 후보를 정확히 확인하지 못함 |
| `RELUPLEX_MODEL_INVALID` | 최종 후보가 사전 모델 검사부터 통과하지 못함 |
| `SIMPLEX_STALLED` / `STALLED` | 피벗 규칙 전환 후에도 정체와 재방문이 계속됨 |
| `SIMPLEX_ITERATION_LIMIT` / `ITERATION_LIMIT` | 해당 Simplex 호출의 반복 예산 소진 |
| `TIMEOUT` | 전체 검증 deadline 초과 |

`STRICT_INEQUALITY_INCONCLUSIVE`는 엄격 부등식 처리에서 결론을 확인하지 못한 별도의 이유다. 이것도 누적 부동소수점 오차가 발생했다는 직접적인 증거는 아니다.

**피벗이 계속 반복되는 것과 numerical failure는 동의어가 아니다.** 현재 코드는 무한 반복을 관찰해 수치 실패로 판정하는 것이 아니라, 일관성 검사·연산 실패·정체·반복 한도·시간 한도를 각각 별도로 처리한다.

## 11. 정확 검증의 비용 제한

정확 유리수 연산은 분자·분모가 커지면 비싸진다. 현재 검증에는 아래 예산이 있다.

| 항목 | 기본 기준 |
| --- | --- |
| UNSAT 정확 검증의 로컬 시간 예산 | 호출당 0.25초 |
| UNSAT 정확 검증의 연산 예산 | 250,000 카운트 |
| SAT 정확 검증의 로컬 시간 예산 | `min(2.0, 0.25 + size / 200000)`초 |
| SAT 정확 검증의 연산 예산 | `max(250000, 16 * size)` 카운트 |
| 유리수 크기 제한 | 검사 대상 분자·분모 각각 최대 16,384비트 |
| 전체 시간 제한 | 기존 solver deadline 공유 |

여기서 `size`는 경계 변수 수와 원본 행들의 `(계수 수 + 1)` 합이다. 연산 카운트는 내부 예산 계수이지 CPU 명령 수가 아니다. 시간도 검사 지점에서 확인하는 방식이므로 개별 큰 연산을 정확히 그 시각에 강제 중단하는 하드 실시간 제한은 아니다.

로컬 예산 소진은 검증 불확정으로, 전체 deadline 소진은 `TIMEOUT`으로 전달된다. 호출이 많으면 작은 검증 비용도 누적되므로 실행 시간이나 timeout 빈도에 영향을 줄 수 있다. 영향의 크기는 모델별로 측정해야 한다.

## 12. 보장하는 범위와 한계

- 정확 검증은 **인코딩된 float 계수를 정확한 이진 유리수로 해석한 실수 문제**를 대상으로 한다.
- 예를 들어 float `0.1`은 정확한 십진수 `1/10`으로 치환되는 것이 아니라, 그 float가 실제로 표현하는 유리수로 변환된다.
- 실제 ONNX 실행기의 모든 연산 순서·float 반올림·하드웨어 동작까지 검증하는 것은 아니다.
- 최종 API 모델은 정확한 유리수 해를 다시 float로 변환한 근삿값이다. 표시된 값의 float 재계산 잔차와 내부의 정확 해 존재 증명은 구분해야 한다.
- 정확 검증은 인코딩과 탐색 전체에 버그가 없다는 보장이 아니다.
- `UNKNOWN`은 SAT도 UNSAT도 증명하지 않는다. 실제 모순이나 실제 오차의 증거로 읽으면 안 된다.

## 13. 시각화에서 읽는 법

Simplex 패널의 호출 결과는 **개별 Simplex 호출 상태**를 집계한다. 최종 신경망 판정은 DPLL(T)의 solver 상태와 `result.json`의 최종 결과를 확인해야 한다.

그래프 아래의 `1e-9 × max(...)` 안내는 수치 일관성 검사의 기준이다. 이를 “최종 SAT/UNSAT도 그만큼 틀려도 허용한다”는 의미로 읽으면 안 된다.

정리하면, 이 기능의 목적은 판정을 하나 더 만드는 것이 아니라 **신뢰하지 못하는 계산 결과를 SAT/UNSAT으로 잘못 확정하지 않도록 하는 것**이다. 정상적인 입력에서 결과가 이전과 같아도, 경계 사례의 판정 보류와 복구라는 역할은 남아 있다.
